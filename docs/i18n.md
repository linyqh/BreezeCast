# Internationalization (i18n)

The UI uses [i18next](https://www.i18next.com) + [react-i18next](https://react.i18next.com).
Supported UI languages: `en` (source locale, fallback) and `zh-CN`.

## How it works

- `src/i18n/languages.ts` — registry of languages (`code`, native `name`, `messages`). The language
  switcher in the sidebar footer, persistence and fallback are all driven by this list.
- `src/i18n/locales/<code>/*.ts` — one file per feature (`app`, `library`, `episode`, …) plus an
  `index.ts` that assembles them. Keys are `<feature>.<element>`; shared words live in `common`.
- `src/i18n/index.ts` — initialisation and `setLanguage()`. Resolution order on startup:
  saved choice (`localStorage["breezecast.language"]`) → system languages (`navigator.languages`,
  matched by exact tag, then by base language, e.g. `zh-Hans-CN` → `zh-CN`) → `en`.
  `<html lang>` follows the active language.
- `src/i18n/i18next.d.ts` — makes `t()` type-checked against the English source locale, so a
  mistyped key fails `tsc`.
- English is the source of truth. Every other locale is typed `Locale<typeof en>`
  (`src/i18n/types.ts`), so a missing or extra key is a compile error. Plural variants are the only
  exception: a locale supplies the CLDR categories its language needs (`_one`/`_other` for English,
  only `_other` for Chinese).

## Writing translatable code

```tsx
const { t } = useTranslation();
<button>{t("common.save")}</button>
t("library.episodeCount", { count: n });          // plural: episodeCount_one / episodeCount_other
t("voices.deleteConfirm", { name });              // interpolation: "{{name}}"
```

- Never concatenate translated fragments; use one key with interpolation.
- Rich text uses `<Trans>` with named self-closing placeholders (`<kbd/>`), see `agents.skillHint`.
  Keep code samples (`<pause 1s>`) out of translation strings and pass them as components.
- Outside React (module scope, `api.ts`) use `i18n.t(...)`, never a top-level constant that
  captures a translated string — it would not update on language switch.

## UI language vs. content language

The language of the *UI* is independent of the language of the *content* being synthesised
(script, voice description, vocal-event tags such as `[笑]` / `(laugh)`):

- `src/i18n/content.ts` and `VOCAL_EVENTS` in `src/api.ts` are keyed by content language (`zh`/`en`)
  and are **not** translated per UI language.
- Default example content (`sample.*` keys) is looked up with `sampleText(key, contentLang)`, which
  forces the language, so the Design/Clone views can offer both zh and en samples in any UI language.
  The initial content language follows the UI language (`defaultContentLang()`).

## Backend messages

The Rust backend keeps API/error text in Chinese for API clients. Job progress messages also carry
`message_key` + `message_args` (see `Job` in `docs/API.md`); the UI renders them through the
`job.*` keys via `jobMessage()` and falls back to `message` for unknown keys. When adding a new
job message, add a key in every locale and call `Job::set_message(key, args, text)`.

## Adding a language

1. Copy `src/i18n/locales/en` to `src/i18n/locales/<code>` (e.g. `ja`) and translate the values.
   Type the assembled object as `Locale<typeof en>`, like `locales/zh-CN/index.ts` does; `pnpm build`
   (`tsc`) lists anything missing. Add the plural categories your language needs.
2. Register it in `src/i18n/languages.ts`:
   ```ts
   { code: "ja", name: "日本語", messages: ja },
   ```
3. Done — the switcher, persistence, system-language detection and fallback pick it up.
